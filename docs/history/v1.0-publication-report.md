  FAILED tests/test_demo_mode.py::test_meta_reports_runtime_facts

Run: `https://github.com/huangJJ8/airi/actions/runs/35501623187`

**Root cause — a workflow-level variable reaching inside the test suite.** The
workflow set `AIRI_LLM_MODE: demo_mock` for *every* step, pytest included. The
suite is deliberately hermetic: the `settings`/`client` fixtures build
`Settings(_env_file=None, ...)`, precisely so a test cannot depend on whatever a
developer happens to have in `.env`. The consequence is that such a test sees the
**process environment** on the runner but the **field defaults** on a laptop. On
a workstation `AIRI_LLM_MODE` exists only in `.env` and is never exported, so
`llm_mode` fell back to its default `openai_compatible` and the three tests
passed; on the runner the workflow value won, the demo substitute became active,
and all three flipped. This is exactly the "green locally, red in CI" shape the
brief asks to explain rather than paper over.

Reproduced exactly, before changing anything:

```powershell
AIRI_LLM_MODE=demo_mock uv run --frozen pytest -q `
  tests/test_demo_mode.py::test_meta_reports_runtime_facts `
  tests/test_development.py::test_api_missing_llm_configuration `
  "tests/test_reflection.py::test_failures_and_provenance[unavailable]"
# -> 3 failed, 2 warnings in 1.77s   (identical assertion messages)
```

**Fix — remove one environment variable; change no test.** `AIRI_LLM_MODE` is
gone from the workflow `env:` block, replaced by a comment stating the rule so it
is not reintroduced. Nothing is lost: the only tests that want the demo
substitute ask for it explicitly, and the rest assert the *unconfigured* defaults
— which is the behaviour those tests exist to protect.

```text
grep -rn "demo_mock|llm_mode" tests/
  test_demo_mode.py:91             asserts llm_mode == "openai_compatible"        (wants the var gone)
  test_demo_mode.py:101            llm_mode="demo_mock"                          (explicit opt-in)
  test_enterprise_relation.py:166  llm_mode="demo_mock"                          (explicit opt-in)
  test_llm_client.py:15            llm_model="mock-model"                        (explicit)
  test_reflection.py:302           asserts llm_model == "configure-your-model"   (wants the var gone)
```

Re-verified under the post-fix environment:

```text
same three tests, environment without AIRI_LLM_MODE  ->  3 passed in 5.59s
```

No test skipped, no assertion weakened, no dependency changed, no product
behaviour touched: `llm_mode` is still a first-class setting and the demo
substitute is still exercised. Only the CI job's ambient override was removed.

### One real defect found and fixed by this verification

Running the launcher under output capture exposed a genuine robustness bug in
`scripts/start-demo.ps1`. Windows PowerShell 5.1 converts **any** stderr line
from a native command into a terminating `NativeCommandError` while
`$ErrorActionPreference = "Stop"` — and `uv` writes progress to stderr. So a
perfectly successful `uv sync` could abort the launcher, for example when a
wrapper, a log capture, or CI merges the streams with `2>&1`.

Fixed by running native invocations with the preference relaxed and deciding on
`$LASTEXITCODE` (real failures remain fatal). The corrected script was then
re-verified end to end: `START_EXIT=0`, both services healthy, endpoints 200,
`stop-demo.ps1` → `PORT 8000 FREE`, `PORT 5173 FREE`. `stop-demo.ps1` already
used `Continue` and did not need changing.

## 19. What Actually Blocked Publication

Three environment faults had to be diagnosed before the first push succeeded. All
three are recorded because each one looks like "git is broken" and none of them is
a fault in this repository.

**1. Commit identity pointed at a non-GitHub address.** The commits were authored
and committed as `<user>@<corporate domain>`, taken from the machine's global git
config. Pushed as-is, every commit would have shown up on GitHub as an unattributed
identity rather than linked to the user's account — a real defect for a portfolio
repository, and one that gets expensive to fix after publication.

Fixed **before** the first push, because the repository was still private and
nothing had been published: all commits were rewritten with
`git filter-branch --env-filter` to the GitHub no-reply identity, the tag was
deleted and re-created, and `refs/original` was dropped and the object store
re-packed. Author dates were preserved. Correctness was checked the direct way —
`git rev-parse <old-tip>^{tree}` and `git rev-parse HEAD^{tree}` are the **same
tree hash**, so only metadata changed, not a single byte of content.

**2. `git credential-helper-selector store` hangs forever.** The push
authenticated successfully, then stalled indefinitely *after* authentication —
so the actual object transfer never started, and the symptom (`git push` appears to
hang with no output) gives no hint of the cause. Isolating the two helper phases:

```text
printf '…' | git credential-helper-selector store   -> timeout, exit 124
printf '…' | git-credential-manager store           -> exit 0
```

The `get` phase is fine; only `store` hangs. Workaround used for the push, without
touching the machine's global config:

```powershell
git -c credential.helper= -c credential.helper=manager push -u origin main
```

(The empty first value resets the helper list, then GCM is added — so the faulty
selector is never consulted. On a stock Git for Windows install this does not
reproduce; it is specific to the bundled PortableGit on this machine.)

**3. A verification probe wrote to the live credential store.** While isolating
fault 2, a harmless-looking probe ran `git-credential-manager store` with a
placeholder value — which *overwrote the real stored credential*. Recovered
without loss because the genuine token had been captured to a pre-probe file whose
only handling was masked, and the restore was verified by comparing hashes rather
than by printing the value. Two lessons, both now house rules: **never call a
`store` verb with test data against a real credential store**, and **a captured
secret must be written to an ignored path, compared by hash, and scrubbed
immediately**.

None of the three is intrinsic to AIRI. They are the reason §5 says "published",
and not "easily published".
